- 评估日期：2026-10-31
- 评估对象：五年计划指标管理平台 · 材料库（`file_info` / `file_ref` / `file_upload_session` + 本地磁盘存储）
- 测试环境：Windows 11 单机、便携 MySQL 8.0.29（127.0.0.1:13306）、Spring Boot 3.5（Tomcat 内嵌）、Python 3.13 基准脚本、本机回环（Loopback）

## 1. 当前存储架构梳理

### 1.1 底层存储引擎
- 实现：`LocalStorageService`（`backend/.../file/service/LocalStorageService.java`），基于 **本地磁盘 NTFS**。
- 抽象：`StorageService` 接口已预留 `MINIO` 对象存储扩展点，但**当前仅有 LOCAL 实现**，未接入任何对象存储。
- 存储键规则：`yyyy/MM/{uuid}.{ext}`，按月份单目录归集，例如 `2026/10/a827….png`。
- 分片临时目录：`{root}/tmp/{uploadId}/{partNumber}`，合并后删除。

### 1.2 文件分片策略
- 前端约定：**> 20MB 自动分片**，每片 **5MB**（`FileService.PART_SIZE`）。
- 会话：`file_upload_session` 记录分片总数、已传分片编号（JSON）、24 小时过期、发起人。
- 可靠性：合并时校验实际大小、魔数、整文件 SHA-256；命中 SHA-256 秒传直接复用既有文件。
- 元数据用途修复：`file_upload_session.biz_type` 于 V9 补齐，合并不再丢失用途。

### 1.3 元数据管理机制（MySQL）
| 表 | 关键索引 | 用途 |
| --- | --- | --- |
| `file_info` | PK(id)、`idx_file_sha256`、`idx_file_status`、`idx_file_uploaded_by` | 文件名、大小、分类、存储键、SHA-256、状态（TEMP/BOUND）、上传人、时间 |
| `file_ref` | UNIQUE(biz_type,biz_id,file_id)、`idx_file_ref_file` | 文件与业务（SUBMISSION/ADJUSTMENT/MILESTONE/INDICATOR）的关联 |
| `file_upload_session` | UNIQUE(upload_id)、`idx_upload_session_sha256` | 分片续传会话 |

- 材料库列表当前实现（`MaterialService.list`）：**一次性读取全部 `file_ref`，在 Java 内存中联表、过滤、排序、分页**。

### 1.4 磁盘容量规划现状
- **无配额、无水位告警、无冷热分层**；仅 TEMP 文件 24 小时未绑定自动清理。
- 备份：`deploy/backup-mysql.sh` 仅 `mysqldump` 数据库，**不包含任何文件内容**。

## 2. 基准测试结果

### 2.1 单文件大小上限支持能力

| 用例 | 结果 | 量化数据 |
| --- | --- | --- |
| 30MB PDF 直传 | ✅ 成功（修复后） | 见下方问题记录 |
| 60MB MP4 直传 | ❌ HTTP 413 / 80002 | 超过 Spring `max-file-size=50MB`，直传被拦截 |
| 120MB MP4 分片上传 | ✅ 成功 | **24 片 × 5MB，0.74s，162.94 MB/s（回环）** |

- 各类上限（`FileTypeRegistry`）：文档/PDF **50MB**、图片 **20MB**、视频 **500MB**、压缩包 **200MB**。
- 结论：**> 50MB 必须走分片**；分片通道实测可稳定承载 100MB+ 文件，视频上限 500MB 是当前设计天花板。

> 测试中发现并修复一个真实缺陷：客户端未携带 MIME 类型时，直传因 `file_info.mime_type` 非空约束失败（HTTP 500）。已在 `FileService.upload` 增加 `application/octet-stream` 回退。

### 2.2 百万级小文件元数据索引查询性能（100 万行实测）

独立表 `file_info_bench`（结构与索引同 `file_info`）写入 **1,000,000** 行后测试：

| 指标 | 结果 |
| --- | --- |
| 批量插入吞吐 | **99.88s 插入 100 万行 ≈ 10,012 行/s** |
| 按 `id` 点查 | 平均 **0.507ms**，p95 **1.105ms** |
| 按 `sha256` 索引查询（秒传判定） | 平均 **0.384ms**，p95 **0.705ms** |
| `status + deleted` 过滤并按 `uploaded_at` 排序取 50 条 | 平均 **1303ms**，p95 **1502ms** ⚠️ |
| `COUNT(*)` 全表 | **572.65ms** |

- 结论：**主键与 SHA-256 索引在百万级下依然是亚毫秒级**，元数据本身不是瓶颈；
- **瓶颈 1**：`status` 低选择度 + `ORDER BY uploaded_at` 缺少复合索引，触发大规模扫描与 filesort，百万级下单次分页查询超过 1.3 秒。
- **瓶颈 2（更严重）**：材料库列表是**全量 `file_ref` 读入内存**再做过滤分页，百万级关联记录会导致内存暴涨与接口超时，当前实现无法直接承载海量数据。

### 2.3 文件系统小文件性能（10 万文件实测）

| 目录形态 | 写入吞吐 | 随机读取吞吐 | `listdir`（10 万项） |
| --- | --- | --- | --- |
| 单目录 flat | 75.98s ≈ **1316 文件/s** | **1536 文件/s** | 33ms |
| 现行 `yyyy/MM` 嵌套 | 90.87s ≈ **1100 文件/s** | **1622 文件/s** | 32ms |

- 结论：NTFS 在 10 万级文件下读写与目录枚举均可接受，**单月单目录不是主要瓶颈**；真正的限制是**单盘容量、单点故障与全量备份/遍历成本**。

### 2.4 并发上传下载吞吐（本机回环）

| 场景 | 并发 | 结果 |
| --- | --- | --- |
| 上传小图片（约 1.5KB × 60） | 12 | 60/60 成功，0.49s，**123.4 文件/s**，平均延迟 86.9ms |
| 下载签名原始流（×200） | 20 | 200/200 成功，0.28s，**723.4 请求/s**，平均延迟 24.1ms |

- 结论：应用层（Tomcat + 本地磁盘）在回环下并发处理余量充足；生产瓶颈将转移到**广域网带宽、磁盘 I/O 与数据库连接池**，而非接口逻辑。

## 3. 可靠性与扩展能力评估

| 维度 | 现状 | 评价 |
| --- | --- | --- |
| 容量线性扩展 | 单块本地磁盘，不能在线扩容；无对象存储分桶 | ❌ 不具备 |

## 4. 可承载阈值与性能瓶颈结论

**当前实现（本地磁盘 + 内存检索的材料库列表）**

- 单文件：**直传 ≤ 50MB；分片 ≤ 500MB（视频）**。
- 元数据：百万级索引点查无压力。
- **材料库可用文件量级：建议 ≤ 10 万条关联记录**。超过该量级后，`MaterialService.list` 全量加载内存的写法会显著拖慢甚至 OOM；`status + uploaded_at` 分页在百万级已达 1.3s。
- 本地磁盘：10 万文件读写正常，但无扩容与冗余，**不适合直接承载甲方海量（百万级以上）生产数据**。

**核心瓶颈点（按优先级）**
1. 材料库列表全量 `file_ref` 内存检索 —— 海量下首要瓶颈。
2. 缺少 `(status, deleted, uploaded_at)` 等复合索引 —— 百万级分页 1.3s。
3. 本地磁盘单点、无副本、无文件备份 —— 可靠性硬伤。
4. 应用服务器中转上传下载 —— 大文件高并发时带宽与连接占用。

## 5. 支撑海量存储的优化改造方案

### 5.1 查询与索引（必须优先，改动小收益大）
1. 材料库列表改为 **SQL 联表分页**：以 `file_ref` 关联 `file_info`、`submission`/`indicator`，在数据库层完成 `indicatorId/unitId/category/keyword` 过滤与分页，禁止全量读入内存。
2. 增加复合索引：
   - `file_info(status, deleted, uploaded_at)`；
   - `file_ref(biz_type, biz_id, file_id)` 已唯一，补充 `file_ref(file_id, biz_type)` 以支撑按文件反查。
3. 大表分页采用**键集分页（seek by id/uploaded_at）**替代深分页 `OFFSET`。

### 5.2 存储引擎升级（海量必需）
1. 基于 `StorageService` 接口落地 **MinIO / S3 对象存储**，按学院或年度分桶，开启版本控制与生命周期规则。
2. **客户端签名直传**：上传/下载改为对象存储预签名 URL，应用只签发凭证，解除应用带宽瓶颈。
3. 视频转码、预览产物迁移到异步任务 + 独立预览桶。

### 5.3 冗余与备份
1. MinIO 分布式 **纠删码（EC）或多副本**，跨节点容灾。
2. 备份策略：对象存储版本化 + 跨区复制；数据库保留 `mysqldump`，并新增**文件-元数据一致性对账任务**（孤儿文件、缺失文件检测）。
3. 增加磁盘/容量水位告警与按学院配额。

### 5.4 并发与吞吐
1. 大文件分片支持**分片并发上传**（当前为串行循环），配合秒传降低带宽。
2. 下载接入 **CDN / 对象存储外链**，签名 URL 直读对象存储而非应用中转。
3. Tomcat 连接池、DB 连接池按压测目标调优；必要时读写分离。

## 7. 总结

当前材料库在**百 MB 级单文件、十万级文件总量、本机中等并发**场景下可用；元数据索引设计良好（百万级点查亚毫秒）。但要支撑甲方**海量（百万级以上）文件存储与高并发访问**，必须完成两项根本改造：**材料库检索 SQL 分页化 + 复合索引**，以及**本地磁盘迁移到具备冗余的对象存储并采用签名直传**。在此之前，系统不具备容量线性扩展与数据可靠性保障能力。
